Token Optimizer reads configuration from two places: environment variables and a `config.json` file. Environment variables take precedence. When both set the same setting, the environment variable wins for that run, and `config.json` holds the persistent default.

For script installs on Claude Code, `config.json` lives at `~/.claude/token-optimizer/config.json`. Plugin installs use the resolved plugin-data directory; other Python adapters use their runtime home/data directory. Do not assume every install writes the legacy Claude path. It stores feature flags, consent status, the pricing tier, and timestamps. The `v5` command and the various `setup-*` and `consent` commands write to it. Most users never edit it by hand; the commands keep it consistent.

## Project config file

A repo can carry Token Optimizer settings for Claude Code cloud sessions in a committed file at `.claude/token-optimizer.json` (under `$CLAUDE_PROJECT_DIR`). In a cloud session the home directory, and with it `config.json`, starts fresh every time, so opt-outs and feature toggles would otherwise reset each session.

The file is read only inside a Claude Code cloud session. On your own machine Token Optimizer ignores it completely: your `config.json` persists there, and a repo you clone never changes your dashboard, pricing tier or feature flags.

Precedence, highest first: environment variable, then your own `config.json` (user or plugin-data), then the project file, then the built-in default. Your own setting always beats the repo's; the project file only fills keys you never set.

Only non-secret preference keys are read: the `v5_` feature gates, `read_cache_enabled`, `daemon_disabled`, `quality_bar_disabled`, `vscode_ext_disabled` and `pricing_tier`. Everything else in the file is ignored, including consent and onboarding markers, which stay per person. Values must be booleans or short strings, and the file must be a regular file (not a symlink) under 64 KB. Token Optimizer never writes this file; commit it by hand. Never put secrets in it.

```json
{
  "v5_bash_compress": true,
  "daemon_disabled": true
}
```

## Claude Code cloud

In a Claude Code cloud session (detected from `CLAUDE_CODE_REMOTE_ENVIRONMENT_TYPE`, `CLAUDE_CODE_REMOTE_SESSION_ID`, the cloud kit, or the pin below; `CLAUDE_CODE_REMOTE=true` alone is not enough) Token Optimizer runs a lean profile: the in-session features (compression, read dedup, archive and expand, checkpoints, trends) work as on the desktop, and the work that cannot help in a throwaway VM is skipped: the dashboard daemon, keep-warm, the status line and hook self-heal writes to `~/.claude/settings.json`, the `cleanupPeriodDays` write, the auto-updater and the first-run welcome. The session-end flush runs inside the hook instead of a detached worker, so its data lands before the VM can be reclaimed. Python bytecode goes to `~/.cache/token-optimizer/pycache`, never into the repo.

| Variable | Default | Effect |
|---|---|---|
| `TOKEN_OPTIMIZER_REMOTE_HOST` | auto-detected | Pin the host: `cloud`, `cowork` or `local` |
| `TOKEN_OPTIMIZER_REMOTE_LEAN` | on in cloud | Set `0` to turn the cloud lean profile off |

## Active compression features

Each active compression feature has a `config.json` key and an environment override. Setting the environment variable to `0` disables the feature for that run regardless of the persisted value.

| Variable | Default | Effect |
|---|---|---|
| `TOKEN_OPTIMIZER_BASH_COMPRESS` | enabled | Set to `0` to disable Bash output compression for eligible read-only commands |
| `TOKEN_OPTIMIZER_COMMAND_FILTERS` | `<runtime-home>/token-optimizer/command-filters.toml` | Path to a user TOML file that adds read-only commands to the compression allowlist and excludes commands you never want compressed; composes with the built-ins, safety-gated, fail-open |
| `TOKEN_OPTIMIZER_READ_CACHE` | enabled | Set to `0` to disable the read cache entirely (no delta, no skeleton substitution) |
| `TOKEN_OPTIMIZER_READ_CACHE_DELTA` | enabled | Set to `0` to disable delta mode only (re-reads return full content instead of a diff) |
| `TOKEN_OPTIMIZER_READ_CACHE_MODE` | `soft_block` | Select the read-cache mode: `soft_block`, `warn`, `shadow`, or `block`. See the modes table below. |
| `TOKEN_OPTIMIZER_STRUCTURE_MAP` | off (measurement) | Set to `beta` to enable structure-map compression event logging. This is a separate measurement toggle, not the mode selector above. |
| `TOKEN_OPTIMIZER_QUALITY_NUDGES` | enabled | Set to `0` to disable the quality-drop alerter |
| `TOKEN_OPTIMIZER_LOOP_DETECTION` | enabled | Set to `0` to disable the retry-loop detector |
| `TOKEN_OPTIMIZER_FIRST_READ_SHADOW` | enabled | Set to `0` to disable both first-read skeleton measurement and active first-read skeleton serving |
| `TOKEN_OPTIMIZER_FIRST_READ_ACTIVE` | enabled | Set to `0` to disable active first-read skeleton serving for promoted cohorts |
| `TOKEN_OPTIMIZER_VERBOSITY_MIN_FILL` | `25` | Gentle lean-output nudge fill floor; below 75% fill it also requires session efficiency below 75. At 75-89% the strong tier uses fill alone; at 90%+ no context is added |

The matching `config.json` keys are: `v5_bash_compress`, `read_cache_enabled`, `v5_delta_mode`, `v5_structure_map_beta`, `v5_quality_nudges`, `v5_loop_detection`, `v5_first_read_shadow`, and `v5_first_read_active` (the `v5_` prefix is a legacy naming convention; the features are current). Manage the `v5_` gates with `measure.py v5 enable|disable <feature>`. The read-cache master gate has its separate environment override.

### Read-cache modes

The read cache operates in one of four modes, selected with `TOKEN_OPTIMIZER_READ_CACHE_MODE` (for example `TOKEN_OPTIMIZER_READ_CACHE_MODE=shadow`). The default is `soft_block`.

| Mode | Behavior |
|---|---|
| `soft_block` | Default. On an unchanged re-read, substitute a compact result (delta or structure map) instead of the full file. May deny an eligible redundant Read and inject its bounded structure map; ineligible reads pass through. |
| `warn` | Allow the full re-read, but emit a warning that the file was already read. No substitution. |
| `shadow` | Measure what substitution would have saved without changing the result the model sees. Used for validation. |
| `block` | Deny redundant reads even without an eligible structure map (reason-only then); safety and escape-hatch checks still apply. This mode table describes the Python Read hook, not the separate OpenClaw config. |

### Checkpoint relevance scorer

These tune `checkpoint_relevance_score`, the IDF-weighted content-overlap scorer that decides which prior checkpoint (if any) a continuation prompt resumes. Every value is **hard-clamped to a safe range at load** — an out-of-range or non-numeric value is coerced into the range rather than trusted — so a mis-set knob can never force the score to a constant or flip the F1 sign. Defaults are calibrated against the real checkpoint pool; change them only with a reason.

| Variable | Default | Safe range (clamped) | Effect |
|---|---|---|---|
| `TOKEN_OPTIMIZER_CHECKPOINT_RELEVANCE_THRESHOLD` | 0.25 | 0.1–0.9 | Minimum score for the pull tool to resume a checkpoint. Lower widens recall (risks vague-continue false matches); higher demands a stronger topical/resume signal. |
| `TOKEN_OPTIMIZER_RELEVANCE_RESUME_BONUS_PRECISION_FLOOR` | 0.5 | 0.0–0.99 | Floor for the precision-scaled resume-intent bonus: effective factor = floor + (1−floor)·precision. Higher protects verbose genuine resumes; lower makes a cross-client graze pay more for its unmatched tokens. |
| `TOKEN_OPTIMIZER_RELEVANCE_PATH_TF_WEIGHT` | 0.5 | 0.0–2.0 | Weight of the path-identity frequency boost (a token recurring across a checkpoint's file paths out-ranks the same word quoted once in prose). 0 disables the boost. |
| `TOKEN_OPTIMIZER_RELEVANCE_PATH_TF_CAP` | 8 | 1–50 | Cap on the per-token path frequency counted by the boost, so one mega-repeated path segment cannot dominate recall. |
| `TOKEN_OPTIMIZER_RELEVANCE_IDF_CAP` | 3.0 | 1.0–100.0 | Cap on each term's IDF contribution, so one ultra-rare token cannot spike the score (keyword-stuffing defense). |

Do not apply Python defaults to the TypeScript extensions merely because an environment name is shared.

| Adapter / name | Native default | Effect |
|---|---|---|
| OpenCode `TOKEN_OPTIMIZER_CHECKPOINT_TTL` | 300 seconds | Checkpoint TTL in the native config |

| OpenCode `TOKEN_OPTIMIZER_FRESH_NUDGE_MIN_FILL` | 50% | Fresh-session nudge fill floor (Python default is 45%) |
| OpenCode `TOKEN_OPTIMIZER_TOOL_CALL_WARN` / `TOKEN_OPTIMIZER_TOOL_CALL_CRITICAL` | 25 / 40 | Tool-call thresholds; explicit null plugin options disable them |
| OpenClaw `TOKEN_OPTIMIZER_CHECKPOINT_COOLDOWN_MS` | 90000 ms | Checkpoint policy cooldown |
| OpenClaw `TOKEN_OPTIMIZER_RUNTIME_EVALUATION_COOLDOWN_MS` | 30000 ms | Runtime checkpoint-policy evaluation cooldown |
| OpenClaw `TOKEN_OPTIMIZER_CONTINUITY_MAX_AGE_DAYS` | 7 days | Prior-session age bound |
| OpenClaw `TOKEN_OPTIMIZER_CHECKPOINT_ROOT` | `~/.openclaw/token-optimizer/checkpoints` | Checkpoint storage location override |

OpenCode plugin options can set feature gates and numeric defaults; environment reads then apply as defined by the adapter. An explicit `dataDir` option wins over its environment value. Pi persists `enabled`, `retainDays` (1-365, default 7), `archiveToolOutput`, and `continuity` in its own `settings.json`; the three boolean gates default off. OpenClaw keeps its own host/plugin config, not Python `config.json`.

## Keep-Warm

Keep-Warm is opt-in and managed by the `keepwarm-*` commands; there are no plain feature-flag environment variables for it. Consent and billing mode are persisted in `config.json` and read by `keepwarm-consent-status`.

Production LLM pinging remains disabled even after consent; there is no supported environment switch here to turn it on. See [Keep-Warm](/features/keep-warm/).

## Archive and savings attribution

| Variable | Default | Effect |
|---|---|---|

### Host environment overrides

| Name | Effect in Token Optimizer |
|---|---|
| `CLAUDE_CODE_AUTO_COMPACT_WINDOW` | Wins over per-model and top-level compact-window settings. Valid explicit windows clamp to 100K-1M and the model limit |
| `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` | Used-percent threshold applied to the resolved compact window; 1 to below 100 compacts earlier. Read-only: Token Optimizer does not delete it |
| `CLAUDE_CODE_DISABLE_1M_CONTEXT` | Exact `1` forces the per-model window resolver to 200K, ahead of its window overrides |
| `CLAUDE_MODEL`, `ANTHROPIC_MODEL`, `CODEX_MODEL` | Model hints where no stronger session model is available |
| `CLAUDE_CODE_DISABLE_MCP_DEFERRED` | Exact `1` disables the deferred-tool assumption in MCP overhead estimation |
| `CLAUDE_CODE_SAVE_HOOK_ADDITIONAL_CONTEXT` | Read-hook persistence signal used by substitution safety/logging |
| `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `HERMES_HOME` | Host-home discovery; validated by the relevant adapter |
| `CLAUDE_PLUGIN_DATA`, `CLAUDE_PLUGIN_ROOT`, `CLAUDE_SESSION_ID` | Host-supplied plugin/session identity, not recommended user tuning knobs |
| `GROK_HOME` | Grok's own home; prefer `TOKEN_OPTIMIZER_GROK_HOME` for a Token Optimizer-only override |
| `MAX_MCP_OUTPUT_TOKENS` | Host output cap used for MCP cap-proximity estimates, not changed by the archiver |

The effective compact window resolves host env, then per-model settings, then top-level settings, then the model's tuned default (about 967K for native 1M). The used-percent override is applied afterward. Context-size overrides and `CLAUDE_CODE_DISABLE_1M_CONTEXT` affect the model limit separately. This is not the generic config.json precedence below.

## Precedence summary

1. Precedence is feature-specific. The per-model window resolver checks `CLAUDE_CODE_DISABLE_1M_CONTEXT`, then `TOKEN_OPTIMIZER_CONTEXT_SIZE`, then `--context-size`; do not assume a CLI flag always beats env.
2. Environment variables win over `config.json` for the run.
3. `config.json` holds the persistent default.
4. Engine defaults apply when nothing else is set.

A value marked `(verify)` anywhere in these docs means the source did not state that detail definitively. Defaults here are source-derived, not proof of live host behavior; beta adapters still require their documented verification.

## Devin

`TOKEN_OPTIMIZER_RUNTIME=devin` isolates shared dispatch from Claude scans. `TOKEN_OPTIMIZER_DEVIN_HOME` overrides the adapter's home; otherwise absolute `XDG_CONFIG_HOME/devin` or `~/.config/devin` is used. Overrides must remain inside HOME and cannot traverse symlinks. Native Windows is refused. Only output filtering is supported (explicit by default, automatic with `install.sh --devin --auto`), not generic dashboard/trends commands. Automatic mode edits only the `hooks` key of `config.json` in that home; automatic captures are kept 7 days or 200 entries. Numeric estimate retention is 30 days with at most 10,000 rows. Raw-passthrough captures are removed after successful delivery; compressed captures remain available for recovery until explicitly deleted or purged.
